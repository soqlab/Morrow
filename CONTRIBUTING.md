# Contributing to Morrow

Thanks for considering a contribution. This document covers how to get set up, the conventions this
codebase holds to, how to extend the two most commonly extended parts, and what makes a pull request
easy to review.

By participating you agree to the [Code of Conduct](CODE_OF_CONDUCT.md). To report a security
vulnerability, follow [SECURITY.md](SECURITY.md) instead of opening an issue.

## Setup

```bash
git clone https://github.com/soqlab/morrow.git
cd morrow/backend
python -m venv .venv
.venv/bin/pip install -r requirements.txt -r requirements-dev.txt   # .venv\Scripts\pip on Windows
.venv/bin/python -m uvicorn app:app --port 8001
```

Python 3.11. No `.env` is needed — the server starts unconfigured on SQLite and tells you what is
missing at `GET /health/deep`. Copy [`.env.example`](.env.example) to `backend/.env` when you want
to change something.

There is no front-end build step. The console is vanilla JavaScript served as-is from
`backend/static/`, so editing a `.js` or `.css` file and reloading the page is the whole loop.

## Running the tests

```bash
cd backend
pytest -q                           # whole suite, no credentials or services needed
pytest -q test_scanner_accuracy.py  # one file
pytest -q -k cbom                   # by name
ruff check .                        # lint; rules live in backend/ruff.toml
```

The suite must pass with nothing installed and no secrets set. Tests needing a real service skip
rather than fail; set `MORROW_TEST_PG_DSN` or `MORROW_TEST_REDIS_URL` to make them run:

```bash
docker compose -f backend/compose.yml up -d postgres redis
MORROW_TEST_PG_DSN=postgresql://morrow:morrow@localhost:5433/morrow pytest -q
```

**A new test must not require a credential or a network call to pass.** If the thing you are testing
genuinely needs one, guard it with `pytest.mark.skipif` on the environment variable and make the
skip reason say which variable enables it. A test that fails on a clean checkout is worse than no
test, because it trains people to ignore red.

## House style

These are not arbitrary preferences. Each exists because its absence caused a specific problem.

### Comments explain *why*, never *what*

The code already says what it does. A comment earns its place by recording the reason a reader would
otherwise have to rediscover: the constraint that forced this shape, the obvious approach that does
not work, the bug this guards against. Prefer a comment that would stop someone "simplifying" the
code back into a defect.

```python
# Gate on MORROW_ENVIRONMENT, which is what app.py actually reads. This block previously tested
# PRODUCTION_ENVIRONMENT=true, a name nothing in the application sets, so the pre-flight checks
# never ran on any deployment.
```

That is the standard. `# check environment` is not.

If you fix a bug, say in the comment what the broken behaviour was. `backend/ruff.toml` and
`backend/entrypoint.sh` are good examples to read before writing your first one.

### Never invent data

No placeholder numbers, no sample rows that look like measurements, no "typical" values standing in
for something unmeasured. If the platform cannot determine a value, the value is unknown and the API
and UI must say so. A scanner that guesses is worse than one that reports `"unobserved"`, because a
guess gets acted on.

This extends to documentation: do not write a figure into a doc that no test or measurement
produces.

### Honest empty states

A workspace with no scans shows "no data yet", not a zero, not a flat chart, not an example estate.
A score with insufficient input says so rather than scoring. Zeros are measurements; absence is not.

### Confidence is part of a finding

`policy.make_finding()` takes `confidence` and `confidence_reason`. Fill them in. A high-severity
finding derived from a weak signal must say which it is, because a reviewer needs to know whether to
trust it.

### Errors degrade, they do not crash

An optional subsystem that is unavailable leaves its field unobserved and keeps the rest of the scan
working. Probes are advisory: a TLS extension probe that times out must not fail the certificate
scan around it. Never swallow an exception silently — log it and record that the field is unknown.

### Secrets

Never log a credential, never return one in an API response, never put one in a test fixture that
looks real. Integration credentials are sealed with `vault_crypto` before storage. If a feature
cannot seal a secret because no vault key is configured, it refuses to save rather than storing it in
the clear.

### Other conventions

- Type hints on anything public. `from __future__ import annotations` at the top.
- Guard clauses: `if not x: return None` on one line is house style (ruff E701/E702 are off for this).
- Line length 120.
- SQL is written out, not generated by an ORM query builder. Parameterise everything.
- Both database back ends must behave identically. If you touch the data layer, test against
  Postgres too — a constraint failure aborts the transaction on Postgres but not on SQLite, and that
  difference has bitten before.
- No new runtime dependency without a reason in the pull request. Several things here are
  hand-written specifically to avoid one (the QR encoder, the TLS ClientHello probe), and the console
  has no third-party JavaScript at all.

## Adding a scanner check

Checks are policy rules evaluated against the facts a probe collected, in `backend/policy.py`.

1. **Collect the fact**, if it is not already collected. Probes live in `backend/scanner.py` and
   write into the facts dictionary. A probe must have a timeout, must never raise into the caller,
   and must leave its field absent rather than guessed on failure.
2. **Write the rule** in `backend/policy.py`, emitting with `make_finding()`:

   ```python
   if _rsa_key_size(facts) and _rsa_key_size(facts) < required:
       findings.append(make_finding(
           rule_id="rsa-key-too-small",
           title=f"RSA key is {bits} bits, policy requires {required}",
           severity="high",
           remediation="Reissue the certificate with a larger key, or migrate to ML-DSA.",
           pq_mapping="NIST IR 8547 deprecates RSA-2048 from 2030.",
           evidence={"observed_bits": bits, "required_bits": required},
           confidence="high",
           confidence_reason="Key size read directly from the certificate.",
       ))
   ```

   `rule_id` is stable and is what remediation tracking keys off, so do not rename one casually.
   `evidence` must contain what was actually observed, so a reviewer can check the conclusion.
3. **Decide whether it is quantum-relevant.** If the finding changes post-quantum exposure, extend
   `derive_pq_relevance` and `derive_quantum_readiness` rather than only raising severity.
4. **Test it both ways** — a case that fires and a case that must not, plus a case with the fact
   missing, which must produce no finding rather than a false positive. Add ground-truth cases to
   `backend/test_scanner_accuracy.py` and update
   [docs/SCANNER_ACCURACY_AUDIT.md](docs/SCANNER_ACCURACY_AUDIT.md) if measured accuracy changes.

## Adding an AI adapter

The AI layer is deliberately provider-agnostic: nothing above `backend/services/llm/` names a
provider. Full detail is in [docs/AI_PROVIDERS.md](docs/AI_PROVIDERS.md).

1. Subclass `base.Provider` in a new module under `backend/services/llm/`. Implement `id`,
   `capabilities()` and `complete()`; implement `stream()` if the provider supports it. If it speaks
   the OpenAI chat-completions shape, reuse `openai_shape.py` instead of writing the wire format
   again.
2. Make every HTTP call through `transport.py`. It is the single network boundary and carries the
   timeout, retry and redaction behaviour; a direct `requests` call bypasses all of it.
3. Declare capabilities honestly in `capabilities()` — tool use, streaming, system-prompt style,
   context window. Callers branch on these, so claiming tool support that does not work breaks the
   assistant rather than degrading it.
4. Raise `LLMError` with the right kind (`AUTH`, `RATE_LIMIT`, `CONFIG`, `TIMEOUT`, …) so the UI can
   tell an operator what to fix. Put the fix in `remedy`.
5. Register it in `registry.ADAPTERS` and add its id to `config.PROVIDER_IDS`, plus any likely
   spellings to `config.ALIASES`.
6. Document its environment variables in [`.env.example`](.env.example) and `docs/AI_PROVIDERS.md`.
7. Test against a stubbed transport, not the live API. The suite must not need a key.

You do not have to modify the package to bring your own: set `MORROW_LLM_CUSTOM_MODULE` to a module
exposing a `Provider` subclass.

## Pull requests

Before opening one:

```bash
cd backend && pytest -q && ruff check .
```

A good pull request:

- **Does one thing.** A refactor and a behaviour change in one diff cannot be reviewed; split them.
- **Explains why in the description**, not just what. What was wrong, or what could not be done
  before. Link the issue if there is one.
- **Comes with tests** that fail without the change. For a bug fix, add the test that reproduces it
  first, then the fix — the test is the proof.
- **States what you verified and how.** "Ran the suite" plus anything you checked by hand. If you
  could not test something, say so; an honest gap is reviewable, a silent one is not.
- **Leaves no new lint.**
- **Does not reformat code it is not changing.** Whitespace churn hides the real diff.
- **Updates the docs it invalidates**, including `.env.example` if you add a setting and
  `CHANGELOG.md` under `## [Unreleased]`.

Small, well-explained changes get merged. Large unexplained ones tend to stall, so if you are
planning something substantial, open an issue first and we can agree the shape before you write it.

### Commit messages

Say what changed and why in the subject, in plain language and the imperative. The existing history
is the guide — `git log` shows the style. Reference an issue with `Fixes #123` when it closes one.
