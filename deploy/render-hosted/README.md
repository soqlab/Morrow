# Hosted Morrow on Render

**Written for: the operator bringing up morrow.soqlab.com.**

`render.yaml` defines `morrow-app`: one Starter web service (512 MB) with a 1 GB disk, about
$7 a month. The free demo, `morrow-demo`, is a separate service and is not affected.

One container runs the API, the Celery worker with beat embedded (solo pool) and Redis on
localhost; see `Dockerfile` and `start.sh`. Measured locally, the API takes about 170 MB once
pages are loaded. If Render's memory graph sits near 512 MB, move the service to Standard.

## Data: SQLite on the disk

Everything is in `/data/morrow.db` in WAL mode, which lets the API and the worker read while
one of them writes; a writer waits up to 5 s for the lock. Measured locally with two customer
organizations: 110 parallel requests mixing writes and reads finished in 1.2 s with no lock
errors (the only refusals were the trial cap of 60 API calls a minute per organization).

What this gives up compared with Postgres:

- **One layer of customer separation, not two.** Every query is scoped to the caller's
  organization by the application (the multi-tenancy, RBAC and security-review suites cover
  it, and an end-to-end run with two organizations confirmed neither can list or open the
  other's assets or scans). Postgres adds row-level security underneath, so a bug in that
  scoping would still be refused by the database. On SQLite there is no second layer.
- **One instance.** SQLite cannot be shared between replicas. Scaling out means Postgres.
- **Backups are disk snapshots.** Render snapshots the disk daily and keeps them 7 days;
  restoring one is a support-assisted operation, not a self-service point-in-time restore.

Move to Postgres when either matters: create a Render Postgres database, set
`MORROW_MAIN_DB_BACKEND=postgres`, `MORROW_FEATURE_STORE_BACKEND=postgres` and `DATABASE_URL`,
and migrate the data (`backend/migrate_main_db_to_postgres.py`, `backend/POSTGRES_CUTOVER.md`).
`start.sh` then runs the schema migration before the API starts.

## Values the Blueprint asks for

| Variable | What to enter |
|---|---|
| `MORROW_VAULT_MASTER_KEY` | A Fernet key: `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`. Keep a copy: without it a restored backup cannot be decrypted. |
| `MORROW_ADMIN_EMAIL` | The first customer-side account (owner of the first organization). |
| `MORROW_ADMIN_PASSWORD` | Its password: at least 10 characters including a digit. Only read when the account table is empty. |

Everything else is either in `render.yaml` or generated by Render.

## Operator portal

`/vendor-admin` signs in with a named operator key (`MORROW_PLATFORM_OPERATORS` holds only its
SHA-256) and an authenticator app. The first sign-in asks you to enrol the authenticator; do that
straight away, because the enrolment window closes once the first owner has one. A new key:
`python -m services.platform_operators --name <name> --role owner`.

## Why staging, not production

The production startup check requires customer sign-in through an external identity provider
(RS256 with a JWKS URL). The built-in password sign-in only issues HS256 tokens, so this runs as
`MORROW_ENVIRONMENT=staging`, which keeps MFA and the refusal of the shared platform key. Before
opening sign-ups to the public, work through `docs/LAUNCH_CHECKLIST.md`.

## Email

Mail goes through Resend's SMTP relay (`smtp.resend.com`, user `resend`), sending as
`noreply@soqlab.com`; soqlab.com is verified in Resend. Set two values in the dashboard:

| Variable | What to enter |
|---|---|
| `MORROW_SMTP_PASSWORD` | A Resend API key with sending access (resend.com → API Keys). |
| `MORROW_TRIAL_NOTIFY_EMAIL` | Where to announce new trial requests: your own address. |

With mail configured: approving a trial request emails the invitation, the sign-in screen offers
"Forgot password?" (`/reset-password`, a single-use link valid for 30 minutes that signs the
account out everywhere when used), and each new trial request is emailed to you. Without it,
those fall back to copying links by hand, and password reset is not offered.

`MORROW_SIGNIN_SIMPLE=1` keeps the customer sign-in screen to email, password, "Forgot password?"
and "Request access"; the token fields and server switcher are for self-hosted operators.

## Customer sign-up: self-serve, limited to verified domains

With `MORROW_SELF_SIGNUP=1`, the form at `/trial` creates the organization at once and emails the
invitation; opening it, the person chooses a password (`POST /auth/invite/register`). The email
is the address check. Self sign-up turns itself off, and requests wait for approval in
**Customers → Trial requests** as before, unless all of these hold: mail is configured,
`MORROW_PUBLIC_BASE_URL` is set, and `MORROW_SCAN_REQUIRE_VERIFIED_DOMAINS=1`.

That last one is what makes open sign-up safe. An organization scans only hosts under domains it
has verified (services/domain_verification.py): on `/ui/domains.html` it adds a domain, publishes
`_morrow-verify.<domain> TXT "morrow-verify=<token>"`, and presses Check now. Verifying
`example.com` covers every name under it. IP addresses are refused, since a DNS record cannot show
who owns an address. The rule is enforced inside `scanner.scan_host` and `ssh_scanner.scan_ssh`,
which every scan path calls, and a context that lost its organization is refused rather than let
through. To let a trusted organization (a signed pilot, your own) scan anything, add its id to
`MORROW_SCAN_UNRESTRICTED_ORGS` (comma-separated).

What it does not stop: the owner of a verified domain can point a name under it at any address.
The scan then reaches that address, from an account tied to a verified domain and an email
address, with the trial caps applied.

## Pull requests on the customer's code host

Customers connect their own code host on `/ui/code-hosts.html` with an access token they create
there: GitHub (or GitHub Enterprise), GitLab (or self-managed), Bitbucket Cloud, Azure DevOps, or
Gitea/Forgejo. Nothing has to be registered by the operator. The page links each host's token page
and lists the permissions. Tokens are checked against the host, encrypted with
`MORROW_VAULT_MASTER_KEY`, and never returned. A self-hosted server must be HTTPS on a public
address.

Fixes then open as a pull request (merge request on GitLab) there: **Remediation → Create PR**,
and **Migration Autopilot → Propose fixes from latest scan → Open pull request**, which adds the
generated settings as a new file and says in the description where to include it, rather than
overwriting the server's configuration. Code: `services/code_hosts.py`.

## Domain

Render dashboard → morrow-app → Settings → Custom Domains → `morrow.soqlab.com`, and a Cloudflare
CNAME `morrow` → `morrow-app.onrender.com`, DNS only. `MORROW_PUBLIC_BASE_URL` builds every emailed
link and `MORROW_CANONICAL_HOST` sends any other public name (the earlier `app.morrow.soqlab.com`)
there with a 308. Every name must also be in `MORROW_ALLOWED_HOSTS`.
