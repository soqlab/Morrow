# Data Boundary And Privacy Model

This document defines the product's enterprise data boundary. Attach it to pilot proposals and security reviews so buyers understand exactly what the platform needs, what stays local, and what is never required by default.

## Default Principle

Morrow should ask for the least customer access that still produces defensible cryptographic evidence.

The preferred flow is:

`customer system -> Airlock local collector -> redaction/fingerprinting -> signed evidence -> platform -> Trust Passport`

The platform should not need broad shell access, source-code upload, packet payloads, private keys, customer secrets, or unrestricted network access to prove most readiness outcomes.

## Data Classes

| Class | Examples | Default Handling |
| --- | --- | --- |
| Allowed evidence | algorithm family, cipher suite, TLS version, certificate metadata, package hash, firmware hash, CI finding, policy result | Sent to platform as signed evidence |
| Pseudonymous identifiers | salted host fingerprint, repo fingerprint, component fingerprint, device fingerprint | Sent only as salted hashes unless customer opts in to reveal names |
| Optional metadata | service owner, business criticality, repo URL, vendor name, region | Sent only when needed for workflow or reporting |
| Restricted data | source code, packet payloads, private keys, tokens, credentials, secrets, customer records | Not collected by default; blocked by redaction policy |
| Break-glass data | targeted logs or artifacts needed for support investigation | Requires written customer approval, scoped retention, and deletion record |

## Quantum Airlock Boundary

Quantum Airlock is the default customer-boundary integration for low-access enterprise pilots.

It provides:

- One-command install script for Linux or Windows.
- Local collector source included in the generated package.
- Signed payload submission with timestamp and nonce protection.
- Privacy-preserving CBOM fingerprints.
- Firmware provenance proof packages.
- Runtime handshake proofs without packet payload upload.
- Remediation proof bundles that customers can inspect before sharing.

It does not require by default:

- Source code upload.
- Private key upload.
- Raw packet capture upload.
- Full filesystem indexing.
- Persistent interactive shell access.
- Broad cloud account administrator permissions.

## Collection Modes

| Mode | Customer Effort | Access Level | Best For |
| --- | --- | --- | --- |
| Public scan | Very low | Approved external hostnames only | First demo, external exposure |
| Airlock read-only | Low | Local read-only commands and metadata collection | Enterprise pilot default |
| CI/CD buzzer | Low-medium | Build pipeline step with repo-local scan output | Preventing new crypto debt |
| CAM/API transparent proxy | Medium | Gateway or sidecar network metadata only | Runtime crypto coverage without app rewrites |
| Deep integration | High | Repo, cloud, and ticketing permissions | Mature production rollout |

## CAM/API Transparent Proxy Boundary

The CAM package is generated by `/crypto-mesh/middleware-plan`. It can run as a reverse proxy,
sidecar, or egress gateway. The platform itself does not need customer packet payloads or broad
system access.

What may leave the customer boundary:

- service name, SNI, peer label, TLS version, negotiated group, cipher, timestamp
- gateway/sidecar health and handshake counters
- signed runtime proof envelopes

What should not leave the customer boundary:

- packet bodies
- request/response payloads
- private keys
- raw traffic captures
- unrestricted process, filesystem, or cloud inventory

The customer still controls deployment, certificates, destination CIDRs, DNS/load-balancer routing,
and rollback.

## Redaction Guarantees

Before evidence leaves the customer boundary, the Airlock policy should strip or block:

- Secrets and credential-looking values.
- PEM private keys.
- Source snippets unless explicitly allowed.
- Packet payload samples.
- Full file paths where only fingerprinted location is needed.
- User/customer record samples.

Server-side sovereign redaction provides a second guardrail for API-submitted text.

## Signature And Integrity

Airlock submissions are signed with `MORROW_AIRLOCK_SIGNING_KEY` derived configuration. Production enterprise pilots should set:

```text
MORROW_AIRLOCK_SIGNING_KEY=<64+ character random secret>
MORROW_AIRLOCK_REQUIRE_AGENT_SIGNATURE=1
MORROW_AIRLOCK_MAX_CLOCK_SKEW_SECONDS=600
```

Unsigned evidence can be useful in local development. It should not be trusted for paid enterprise pilots.

## Customer-Controlled Deployment Pattern

Recommended enterprise pattern:

1. Customer reviews generated Airlock package.
2. Customer installs read-only collector in a scoped subnet or CI environment.
3. Customer sends only signed evidence to the platform endpoint.
4. Platform issues Trust Passport, remediation proof package, and compliance ledger entry.
5. Customer decides whether to reveal pseudonymous asset labels.

## Data Retention Defaults

Pilot defaults unless contract says otherwise:

- Scan/evidence records: active pilot plus 90 days.
- Audit/security logs: 12 months.
- Support artifacts: deleted within 30 days after case closure.
- Public Trust Passport shares: revoked on customer request or pilot end.

## Buyer Answer

Short answer for security reviews:

> The platform is designed to operate through a customer-boundary Airlock. By default it receives signed cryptographic evidence, salted fingerprints, and workflow metadata, not source code, secrets, private keys, packet payloads, or unrestricted system access.
